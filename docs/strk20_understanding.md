# How STRK20 and the Starknet Privacy SDK Work

## The Big Picture

Normal ERC-20 tokens on Starknet are fully transparent — everyone can see who holds what, who sent what to whom, and how much. The Starknet Privacy SDK wraps a **privacy pool contract** around standard ERC-20 tokens to make transfers private.

```
PUBLIC WORLD                    PRIVATE WORLD (pool)                PUBLIC WORLD
(everyone sees)                 (encrypted, unlinkable)             (everyone sees)

Alice has 1000 STRK   ---->    Encrypted notes inside pool   ---->  Bob has 500 STRK
[deposit]                      [private transfers]                  [withdraw]
```

## The Core Pieces

### 1. Privacy Pool Contract (Cairo, on-chain)

A smart contract deployed on Starknet that:
- Holds ERC-20 tokens in custody
- Stores encrypted channels, notes, and nullifiers
- Validates STARK proofs before applying any state change
- Calls ERC-20 `transfer_from` on deposits and `transfer` on withdrawals

### 2. UTXO Model (like Bitcoin)

Inside the pool, tokens aren't balances — they're **notes** (encrypted UTXOs). A note is: "500 STRK, encrypted so only Bob can read it." To spend a note, you consume it entirely and create new notes (transfer amount + change back to yourself).

### 3. Channels (encrypted links between users)

Before Alice can send to Bob, they need a shared secret. A **channel** is created using ECDH: Alice's private viewing key + Bob's public viewing key = shared channel key. All notes between them are encrypted with keys derived from this channel key.

### 4. Nullifiers (prevent double-spending)

When a note is spent, a **nullifier** (one-way hash) is published. The contract tracks all nullifiers — if you try to reuse one, the transaction is rejected. Observers see "a nullifier was published" but can't link it back to which note was spent.

### 5. STARK Proofs (validity without revealing secrets)

Every pool transaction requires a STARK proof generated by the proving service. The proof says "this transaction is valid — amounts balance, keys are correct, no double-spending" without revealing any private inputs.

## ERC-20 Interaction Points

The pool only touches ERC-20 at two boundaries:

```
DEPOSIT:   ERC-20.approve(pool, amount)  →  pool calls ERC-20.transfer_from(user, pool, amount)
                                             pool creates encrypted note for user

WITHDRAW:  pool spends user's note       →  pool calls ERC-20.transfer(user, amount)
                                             user gets public tokens back
```

**Everything between deposit and withdrawal is zero ERC-20.** Private transfers are just encrypted note reassignment inside the pool's storage. The tokens sit in the pool's ERC-20 balance the whole time.

## The SDK Flow

```typescript
// 1. Setup — connect to pool, prover, and discovery service
const transfers = createPrivateTransfers({
  account, viewingKeyProvider, provingProvider, discoveryProvider, poolContractAddress
});

// 2. Register — publish your viewing key (one-time)
await transfers.build().register().execute();

// 3. Deposit — public ERC-20 → private note
await transfers.build({ autoSetup: true })
  .with(token, t => t.deposit({ amount: 500n, recipient: myAddress }))
  .execute();

// 4. Transfer — private note → private note (fully encrypted)
await transfers.build({ autoSetup: true, autoSelectNotes: "naive" })
  .surplusTo(myAddress)
  .with(token, t => t.transfer({ recipient: bobAddress, amount: 200n }))
  .execute();

// 5. Discover — find notes encrypted for you
const { notes } = await transfers.discoverNotes({ tokens: [token] });

// 6. Withdraw — private note → public ERC-20
await transfers.build({ autoSelectNotes: "naive" })
  .surplusTo(myAddress)
  .with(token, t => t.withdraw({ amount: 200n, recipient: myAddress }))
  .execute();
```

## What Each Step Does Under the Hood

| SDK Call | On-chain Actions | ERC-20 Calls | Privacy |
|---|---|---|---|
| `register()` | Store public viewing key + encrypted private key for auditor | None | Public (everyone sees you registered) |
| `deposit()` | OpenChannel (self) + OpenSubchannel + Deposit + CreateEncNote | `transfer_from(user, pool, amount)` | Entry point is public, note is encrypted |
| `transfer()` | OpenChannel (if new) + UseNote + CreateEncNote (recipient) + CreateEncNote (change) | **None** | Fully private — all encrypted |
| `withdraw()` | UseNote + Withdraw | `transfer(pool, user, amount)` | Exit point is public |

## Infrastructure

```
User (browser)
  └── TypeScript SDK (builder API)
        ├── Discovery Service (Rust/Axum, stateless)
        │     "Here's my viewing key — what notes do I have?"
        │     Scans pool storage, decrypts matching channels/notes
        │     Forgets the key immediately after each request
        │
        └── Proving Service (Starknet OS)
              Executes transaction in a virtual Starknet block
              Generates STARK proof that everything is valid
              Returns proof for on-chain submission
```

## The Privacy Guarantee

- **Inside the pool:** sender, recipient, amount, and token type are all encrypted. Observers see opaque ciphertext and one-way hashes.
- **At the boundaries (deposit/withdraw):** who deposited and who withdrew is public. The privacy comes from the fact that you can't link a specific deposit to a specific withdrawal.
- **Compliance:** an auditor holds a key that can decrypt everything. This is enforced at the contract level — the current contract requires a non-zero auditor key.
